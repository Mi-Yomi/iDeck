## Команда: четыре подагента

Используй свою команду из **4 подагентов**. Ты координируешь работу, собираешь изменения, проверяешь итог и управляешь Codemagic. Если доступный лимит среды ниже, выполни эти роли очередями и честно укажи фактический состав команды.

1. **Native dependencies и QEMU.** Проверяет первый реальный отказ native recipe, pinned sources, patches, configure/build flags и arm64 iOS outputs. Готовит минимальное исправление причины по полному логу.
2. **Swift, Xcode и IPA.** Проверяет target, реальные зависимости при линковке, embedded libraries, extensions, guest resources, bundle IDs и упаковку. Не заменяет требуемые компоненты заглушками.
3. **Независимая проверка.** Читает изменения первых двух, запускает подходящие regression/negative tests, проверяет hashes и сохранение защитных проверок. Отделяет host-проверки от Apple compiler/linker результатов.
4. **Артефакты и продолжение проекта.** Собирает логи и provenance, готовит сводку для `HANDOFF.md`, проверяет наличие и состав артефактов. Пока ждём CI, может изучать следующий шаг с glibc/Steam ARM64, не меняя основной build path и не отвлекая команду от IPA.

Раздай непересекающиеся файлы или отдельные рабочие копии. На Windows они должны быть на E:. Согласовывай изменения общих lock/script files перед интеграцией. Только координатор коммитит объединённый результат, пушит рабочую ветку и запускает CI. Четыре подагента не означают четыре параллельные macOS-сборки.

## Следующий запуск Codemagic

Сначала проверь, нет ли уже активного запуска нужной ветки. Если есть — следи за ним, не создавай дубль. Страница приложения: [Codemagic iDeck](https://codemagic.io/app/6ad03ce9a8a969b53f3a4aa9).

Перед **каждым** запуском проверь:

- Выбран приватный `Mi-Yomi/iDeck`.
- Осталось **не менее 120 бесплатных macOS минут**, платная подписка/оплата отключена. Не ставь подтверждающий input по старой проверке или предположению.
- Все нужные изменения закоммичены и pushed; локальный checkout чистый, полный HEAD совпадает с SHA удалённой рабочей ветки.

Сначала выбери ветку `codex/linux-guest-feasibility-20261015`, затем workflow **`ideck-linux-probe-ipa`**. Передай:

```text
expected_commit=<полный текущий SHA проверенной pushed ветки>
native_build_approved=true
free_quota_verified=true
private_source_verified=true
```

Последние два `true` допустимы только после реальной проверки условий. Установка предусмотренных recipe build tools, pinned Rust toolchain и загрузка исходников на одноразовом runner входят в эту задачу. Не ослабляй проверки branch/repository/commit и не меняй безопасные defaults workflow.

Лимит провайдера — 120 минут, внутренний бюджет worker — 6900 секунд. Это ограничение, а не обещание длительности. Не увеличивай лимиты и не подключай оплату. Запускай только одну сборку одновременно, в пределах проверенной бесплатной квоты. Отдельная Swift-only проверка обычно не нужна: IPA workflow уже запускает её первой.

Не используй повторный запуск старой сборки с `main` или старым SHA. После старта проверь фактический `checkout_commit` и `IDECK_BUILD_REQUEST`; неверный checkout не считается проверкой наших изменений.

## Как продолжать после ошибки

1. Сохрани URL, полный SHA, первый упавший `IDECK_BUILD_STEP`, исходный лог и доступные `result.json`. Найди первую причину, а не только последнюю строку `Build failed`.
2. Исправь причину минимально и добавь содержательную regression-проверку, если ошибка может повториться. Запускай подходящие локальные проверки. Не трать время на повторение уже пройденных тяжёлых проверок без новых изменений или подозрений.
3. Проверь diff, hashes/provenance там, где менялись входы; закоммить, push, проверь новый remote SHA. Затем снова проверь квоту и запускай следующий build на этом SHA.
4. Не повторяй ту же сборку вслепую. Повтор без изменения кода допустим только при доказанном временном сбое инфраструктуры, с записанной причиной и новой проверкой квоты.

Не отключай `data_filter`, не переходи на `fully_trusted`, не глуши patch/compiler/linker errors и не подставляй фиктивные библиотеки ради зелёного статуса. Новая проблемная запись архива требует отдельного разбора, а не расширения исключения на весь каталог. При изменении source pins обновляй locks и объясняй совместимость; не переключайся незаметно на latest.

Не считай старый binary, simulator output или готовую чужую IPA доказательством нашей сборки. Если используешь сохранённые native products, сначала докажи соответствие исходникам, patches, toolchain, architecture/SDK и digest; иначе собирай заново.

## Что считать результатом

Успех ближайшего этапа — одновременно:

- `LINUX_IPA_BUILD_RESULT.status == "linux_probe_ipa_built"` на правильном SHA.
- Реальные успешные native compilation, Xcode linking и package validation в логах.
- Доступная **`iDeck-Linux-Probe.ipa`** с проверенными размером и SHA-256, настоящими libraries и guest assets.

Сохрани артефакты Codemagic:

```text
.work/build-request/result.json
.work/linux-profile-apple/result.json и логи
.work/linux-ipa/result.json и логи
.work/linux-ipa/iDeck-Linux-Probe.ipa
.work/linux-ipa/native-products.tar.gz, если создан
.work/linux-ipa/husk/build/logs/
```

Если доступен мой компьютер, скачай результат в отдельный каталог на E: и сообщи точный путь. Если работаешь только в облаке — сохрани артефакт там и дай доступную мне ссылку; не утверждай, что файл уже на E:. Не коммить IPA, большие build trees, кэши, cookies, токены или сертификаты. В Git нужны код, проверки, осмысленные manifests/evidence и документация.

Ad-hoc IPA ещё потребует моего обычного sideload signing. Даже собранный IPA сам по себе не доказывает запуск Linux на iPhone, работу JIT/GPU или запуск Steam. Эти пункты отмечай отдельно как непроверенные до реального device test. После первого успешного IPA сохрани проверенную ревизию и артефакты. Дальнейшие исследования Steam не должны ломать полученную сборку.
